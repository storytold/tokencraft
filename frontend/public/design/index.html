    Scope and retries
    Use the same authorized project, idempotency key, and normalized intent to recover an admitted request. Follow the returned Location.
    Successful replies
    Quote previews return 200. New durable submissions return 202. An identical retry returns the original receipt with 200.
    Submission rate
    New requests share an organization bucket. The default is 120 requests per minute with a burst of 20. Inspect the rate-limit response and its Retry-After delay.
    Units and cursors
    Check whether a field uses nano-USD, micro-USD, or a decimal string. Request history uses next_after. Management lists may use next_before. Continue with the same filters and scope.
    Response formats
    Native errors use error.code and error.message. Compatible text errors and MCP have distinct envelopes. Artifacts are binary, export pages are versioned NDJSON, and chat uses SSE when requested.

    State, identity, and storage
    Gateway request
    Account + project + actor scope the idempotency key. The request ID scopes the customer-facing lifecycle. Client scope applies when present.
    Provider run
    The gateway request identifies the run. Binding, upstream model, credential pin, lease, and provider handle govern execution. The handle can arrive after gateway admission.
    Results
    Media slots bind bytes and metadata to the gateway request. Chat chunks add an ordinal. The turn lane coordinates fair scheduling with each claim.
    Lifecycle
    Queued work can start, expire, or be canceled. Running work can succeed, fail, or await reconciliation. Verified fal evidence can return some unconfirmed runs to polling. A successful gateway result follows result persistence.
    Accounting
    Admission reserves an estimate. Provider observations and supplier settlements keep their own evidence. Webhook delivery also advances independently.
    Validation, quality, and customer settings
    Unsupported fields
    Scoped media uses a strict request schema. Chat recognizes unsupported field names and returns an error. Supported aliases and defaults normalize to typed input. Provider-specific request construction forwards the fields the adapter accepts.
    Customer policy
    Resolve request preferences, then project settings, then organization settings, then applicable defaults. Both sets of hard bounds apply. Provider access also checks organization sharing, project exclusions, and applicable region and retention requirements. A client can have a separate monthly budget.
    Quality
    A configured quality floor can gate automatic selection using the community average and at least 10 ratings. Six on the 10-point scale represents three out of five stars. An optional usage floor adds a separate distinct-account test. Those are pre-dispatch signals. The worker checks output type and integrity during publication.
    Already admitted
    A matching authorized replay returns the existing request. A queued, unsubmitted run still faces the current provider and connection policy before sending.

    Lease, fallback, and what to measure
    Work ownership
    PostgreSQL grants a run in one claim transaction. A 40-second submission lease and a separate 20-second connector polling lease guard state changes. An expired, unacknowledged run can become unconfirmed.
    Compute failure
    Configured chat targets have process-local cooldowns. A connection-establishment failure or guaranteed pre-acceptance 429 can advance to an allowed target within the retry window. A lost response after possible acceptance or interrupted stream preserves the original evidence.
    Provider failure
    Use the adapter’s accepted handle and status or recovery API. Observe acknowledged work at its original connector. A provider-side outage can require reconciliation even while every compute target is healthy.
    Optimization proposal
    Measure claim wait and database pool pressure, dispatch to provider acceptance, acceptance to first token or completed job, artifact publication, and customer delivery separately. Keep the claim transaction short and bound concurrency. Consider wakeup hints with periodic polling as a recovery path only if measured queue wait or empty polls justify them.

    Cell architecture and failover

    Decision. Standardize TokenCraft’s transactional store on PostgreSQL. Use the same schema and request lifecycle in the self-hosted single-cell install and each hosted cell. Use a supported major that passes TokenCraft’s migration and recovery suite.

    Why PostgreSQL. Admission commits request identity, idempotency, estimated spend reservation, and queued work together. Row locks and leases coordinate claims. Relational constraints and queries fit project scope, usage, settlements, and audit. Its permissive open-source license and standard deployment let operators run it themselves or use managed PostgreSQL. TokenCraft already uses these transactions and migrations. TokenCraft design · PostgreSQL license · Transactions · Row locking

    MySQL / InnoDB
    Suitable for the same transactional queue pattern and familiar to Studio. Porting TokenCraft’s queries and migrations buys operational consolidation. A Studio API adapter can integrate while each service keeps its existing database. MySQL locking reads
    DynamoDB
    Viable for predictable key-based access in a managed deployment. TokenCraft would have to remodel fair job selection, organization limits, and usage queries around keys and maintained projections. A dependency on the managed service would change the standalone distribution. DynamoDB transactions
    CockroachDB / Spanner
    Revisit if one organization needs strongly consistent writes across regions in one logical database. Validate SQL behavior, regional write latency, and operating cost against the same workload. CockroachDB placement · Spanner configurations

    Home cell and compute placement

    Intended flow. Axum commits the request in the home cell’s PostgreSQL database. A worker in that cell claims it. For a self-hosted route, the worker calls the cell’s inference pool. For a managed route, the worker submits through a connector to an external provider such as fal or Kinovi. The cell worker records the result and publishes any artifacts in either case. Inspect the self-hosted path · Inspect the outsourced path

    Proposal. Use a static cell assignment for self-hosting and a durable account_id → cell_id directory for hosted routing. Spread a hosted cell’s API and workers across independent availability zones or equivalent failure domains. Its highly available PostgreSQL writer and reachable artifact store own request identity, budget, leases, status, artifacts, and delivery. Add cells for capacity or residency. Each owns its organizations’ work and gets an explicit share of shared provider quotas. Inspect cell routing

    Single-cell deployment with one API replica. Trusted HTTPS ingress can send traffic directly to the private Axum listener. New HTTP requests can fail while the only API replica is unavailable. Separately running workers can keep claiming committed jobs while PostgreSQL is reachable. Inspect direct ingress

    Cell API load balancing. The supplied private HAProxy configuration sits after trusted HTTPS ingress and discovers one cell’s API replicas through DNS. It sends requests to replicas that pass /ready, streams responses, and returns 503 when the pool is unavailable. Run redundant proxy instances across the cell’s failure domains. The proposed organization router selects the cell. PostgreSQL still distributes queued work, and model routing still selects compute. Inspect the load balancer · Deployment and validation

    Self-hosted text routing. One self-hosted OpenAI-compatible text offer can name up to four endpoints in the cell’s configuration. Lower priority numbers come first. Equal-priority destinations share requests by a stable hash of the request and target IDs. Both the API and workers need the same binding revision because admission pins its digest. Keep the logical offer and quote stable across endpoints. Validate that every target serves the same model contract and that the quote covers its cost. Compute routing design and configuration

    Placement contract. Assign self-hosted inference capacity to the same home cell as its workers, typically in the primary region. Workers and model replicas can run in separate services and scale independently. A warm target in another approved zone, region, or infrastructure provider can be reserved for the same logical cell. The current binding checks the declared provider and region pair, with the provider ID recorded in the cloud field. Operators verify the processing location and enforce tenant placement policy. Inspect compute placement

    Capacity control proposal. Manage the home cell’s own model replicas and keep ready capacity across independent zones. Use readiness probes, queue age, spare slots, and classified compute failures to guide scaling. Shift eligible work to ready targets first, then replenish the reserve asynchronously through the cluster or infrastructure autoscaler. Admit new targets after model readiness, policy, quota, and binding checks. Keep the last known good binding available for admitted work. Managed inference providers scale their own compute. Inspect capacity control

    Safe fallback. The current text path can advance after connection establishment fails or a target returns an explicitly opted-in 429 that guarantees rejection before execution or billing. It starts fallback attempts within a bounded deadline and honors the worker lease. Cooldowns are process-local. Ambiguous transport, a 5xx, or interrupted SSE follows the original outcome rules. An acknowledged fal or Kinovi job retains its original handle. Deploy matching binding revisions and drain pinned work before replacing a stack.     Read the request’s execution path

    In Requests or Compare, the trace extension records each self-hosted chat compute attempt. Select a target to see the worker’s submission timing, configured priority, and response status when recorded. The first successful response headers mark the start of a response. The request outcome records completion separately. Inspect endpoint fallback · Trace extension source

    Provider offer
    The model contract and price selected at admission. Offer retries can change it.
    Home cell
    The configured owner of the request, PostgreSQL state, and lease. Endpoint fallback keeps the same owner.
    Compute target
    The chosen endpoint within a stack. Its compute provider, execution region, and zone come from operator configuration at dispatch.
    Inference provider
    The identity reported by the upstream service when available. Older requests and managed providers may have no recorded compute placement.

    Failure boundaries

    Compute endpoint or zone
    The home cell stays active. Use another approved endpoint if the adapter classifies the attempt as safe. Reserve ready capacity in surviving zones.
    Compute region
    A reachable home cell can use a warm, approved regional standby assigned to that cell. Verify model readiness, quota, residency, and connectivity ahead of time.
    Home-cell region
    Fence the old writer and dispatch, then promote the standby for the same logical cell and move ingress. Recover PostgreSQL, artifacts, keys, and callback routes. Asynchronous replication can leave acknowledged writes behind. Reconcile provider attempts that may be missing after the verified recovery checkpoint before resuming dispatch.
    Compute provider outage
    A reachable home cell can use approved standby capacity reserved for it with another infrastructure provider. If the outage also takes down the home cell, recover its database and artifacts, plus ingress, DNS, identity, secrets, and observability, in a separate failure domain before resuming dispatch.

    Capacity and verification. Keep enough warm model capacity to absorb the planned loss. Use cold scaling to replenish it. Before setting availability targets, drill endpoint loss, compute-region loss, fenced cell recovery, and recovery across providers. Measure admission availability, time to first token, completion rate, duplicate upstream jobs, and recovery time and recovery point for acknowledged requests. Track queue and pool waits separately so persistent dispatch pressure can justify a dedicated wakeup queue while PostgreSQL remains authoritative.

    Studio pilot and dual-store transition

    Proposal. Keep both request readers active. Route each new eligible Studio request to TokenCraft’s PostgreSQL at admission. Read older Studio jobs from MySQL and existing TokenCraft requests from PostgreSQL. Each job keeps one execution and status owner for its lifetime. Studio’s API continues to expose the compatibility view. Explore the transition

    Observed. Studio’s session-job reader uses MySQL. The scoped TokenCraft gateway exposes authorized request detail, history, results, and artifacts. Its migrations include both the earlier jobs schema and the scoped gateway requests schema. Inventory which PostgreSQL request families are populated and visible to Studio before enabling their readers. Keep their current APIs and IDs available. Studio session reads · Scoped TokenCraft reads

    Pilot scope. Start with one approved Studio image workflow behind a per-project flag. Studio owns customer credits and media visibility. TokenCraft records estimates and supplier evidence. Confirm status and error compatibility, asset lifetime, and one wallet outcome per request before expanding. Pilot plan

    Ownership during coexistence

    Existing MySQL jobs
    Continue to read updates, status, and result links through the Studio reader. Existing workers and callbacks complete and reconcile their original jobs in MySQL.
    Existing PostgreSQL requests
    Keep their current request ID, scope, and supported readers. Link a request into Studio history only when a verified Studio identity and request alias establish ownership. If an older PostgreSQL request family is in use, give it its own reader and origin value.
    New migrated Studio requests
    Keep the request, queue lease, provider handle, and result state in TokenCraft’s PostgreSQL. Retain the external Studio token through an explicit alias. PostgreSQL holds the new job record. MySQL remains responsible for Studio sessions, wallet entries, and Studio media metadata.

    Store a durable routing and handoff record scoped to the Studio tenant and operation. It links the Studio token, stable submission key, intent digest, execution owner, and gateway request ID when available. For hosted cells, associate it with the organization’s home cell. Both the legacy and PostgreSQL admission paths for the covered workflow must use the same ownership guard before evaluating rollout flags. The guard serializes concurrent decisions for the same scoped key. Historical tokens with no verified mapping retain their existing duplicate behavior until reconciled.

    Point reads, batch status, and history

    Point reads. Authorize the Studio session or API caller, then resolve the typed request ID or scoped alias through the verified route. Query one owner when known. Resolve an unknown historical token through the bounded set of authorized readers. A confirmed absence can return the existing missing response. A timeout for an unresolved source is retryable. A conflicting alias is an invariant violation for operators to investigate.

    Batch and recent jobs. Group known tokens by owner and keep the current item ordering and per-item response contract. For unified history, run bounded indexed reads from both stores in parallel with the same authorization and filters, then merge by immutable creation time and a deterministic origin-and-ID tie-breaker. Deduplicate by verified logical ID and filter declared mirrors before paging. Use a common read model for the fields Studio needs, then map it to the existing response. Keep an uncertain provider outcome visible as pending or as an explicitly supported reconciliation state.

    Pagination and outage behavior. Preserve the existing bounded recent-jobs response. A paginated unified list uses an opaque, signed cursor with scope, filters, an age cutoff, and the last consumed position for each reader. Each reader must support the same sort and cutoff contract. Live statuses can change between pages. If either reader fails, return a retryable error to clients expecting a complete list. A versioned partial-result contract may expose source coverage and keep the prior cursor. An independently confirmed point read can still succeed when the other store is unavailable. PostgreSQL snapshot semantics

    New requests through PostgreSQL

    1. Record ownership before side effects. Check for an existing owner or a consumed legacy key. For an eligible, genuinely new submission, persist the Studio alias and PostgreSQL route with a scoped uniqueness constraint. Store the intent digest and a retention-governed replay reference. The rollout flag chooses the owner only for a new admission.
    2. Confirm Studio credits. Reserve or deduct in the MySQL wallet once per durable handoff. Persist the ledger reference. After an ambiguous wallet response, resolve that handoff’s ledger entry before proceeding. An idempotent refund or release follows a definitive rejection under Studio’s policy.
    3. Admit to TokenCraft. Use the scoped service identity, verified client mapping, and saved TokenCraft idempotency key. Admission then creates PostgreSQL work eligible for dispatch. Persist the returned gateway ID against the Studio token. If the receipt is lost, replay the same admission instead of re-entering routing. Return the existing Studio response shape at the agreed acceptance boundary.
    4. Publish a Studio result. TokenCraft finishes the original provider run. The adapter fetches output within its retention window, verifies it, and commits the Studio asset with a stable key per job and output slot. Record publication in the compatibility view. Studio exposes success and its own media reference once publication is durable.

    Use a durable next action for each cross-store step. The step’s owner commits its state and next action together. Repeat transport and record reconciliation independently of the provider invocation. Acknowledged work stays with its existing worker and callback routes during retries and deployment changes. Transactional outbox

    Cutover, rollback, and retirement

    1. Inventory and shadow. Confirm the live request families, ID and status contracts, wallet deduplication, and artifact retention. Deploy owner lookup and both readers before enabling new PostgreSQL admissions. Drain writers that can still bypass the ownership guard for the pilot workflow. Compare normalized records and shadow quotes without provider submissions.
    2. Canary one image workflow. Route only brand-new admissions for an approved cohort to PostgreSQL. Retain the legacy readers, provider callback routes, and reconciliation workers. Compare history, point and batch status, asset access and lifetime, and the customer ledger before expanding.
    3. Roll back new traffic independently. Turn off PostgreSQL routing for brand-new submissions. Already recorded owners retain their route. Keep PostgreSQL reads and workers available for those jobs. An unresolved ownership lookup pauses admission for that request with a retryable response, including during rollback.
    4. Drain and prove coverage. Retire legacy execution only after pending and unconfirmed MySQL jobs and ledger entries reconcile. Continue MySQL request reads through the required history window. If terminal history is later copied, use checkpoints plus late-update catch-up, validate identity and result parity, and switch the read location explicitly. Keep MySQL serving the Studio domains it still owns.

    Release gates. Pass a mixed-store history test with equal timestamps, duplicate aliases, and multiple pages. Interrupt each reader independently and confirm there is no false missing response. Drop acknowledgments at the wallet, gateway, and publication steps. Replay across flag changes and verify one owner, one credit outcome, and one provider submission. Roll back with jobs active in both stores and confirm both can finish.

    Track during rollout. Record route choice, source read latency and timeouts, missing or conflicting mappings, handoff age by stage, publication lag, and unresolved ledger items. Join the Studio token, gateway ID, and upstream handle in scoped traces. Expand only after compatibility and recovery checks pass.

    Receipt replay and idempotency

    Observed. A committed native request can be replayed under the same account, project, actor, key, and effective intent. Replay returns the original request ID and status URL with 200, even after routing policy changes. A different intent with the same key returns 409. If the first transaction rolled back, a retry goes through fresh admission under current policy.

    Caller action. Persist the original endpoint, key, scoped identity, body, and intent-bearing headers until the receipt is recovered. Preserve the prompt or input, workload, original quote and offer pin if supplied, client and app references, and delivery choice. Use the saved status URL once known.

    Pilot pass. Drop the response after commit, change policy, and retry. Expect the same ID, one reservation, and one provider submission. Change an intent field and expect 409. Inspect receipt replay

    Provider acknowledgment and artifact recovery

    Provider ACK lost

    Observed. The fal plugin verifies the signed completion and its saved request proof. In operator-key mode it can recover the plugin's missing receipt. The gateway validates the request-bound completion hint and its worker looks up the original connector receipt during the 15-minute recovery window. Tenant-key callbacks require the plugin's saved fal handle. Verify the recovered handle and resumed polling in the request trace.

    Operator action. Hold ambiguous acceptance in awaiting_reconciliation. Resolve the existing provider job using verified evidence. An older or unauthenticated event, conflicting handle, or missing correlation requires investigation. A new submission requires proof of non-acceptance or a documented provider idempotency guarantee. The inspected Studio branch saves its fal-to-job mapping after submission. Its callback lookup fails when the mapping is missing, so record the Studio handoff before crossing the provider boundary in the pilot.

    Pilot pass. Drop the ACK after provider acceptance. Exercise a valid callback, duplicate delivery, and invalid or mismatched evidence. Only the valid evidence recovers the original run. Count one upstream submission. Inspect fal recovery · Inspect Studio lookup

    Storage stalls

    Observed. A provider-completed result stays pending until output bytes are stored and the gateway commits the manifest and succeeded state. Preparation failures defer polling on the existing handle. A poll deadline can move the request to reconciliation. An eligible acknowledged fal or Kinovi job can get one audited recheck within 24 hours of its first polling timeout, using its original binding and available credential.

    Operator action. Open Delivery → Artifact publication in the private Operations console. Provider acknowledgment to observed completion is the provider and polling window. Observed completion to publication is the media and storage window. Compare download, validation, and storage timings with PostgreSQL pool wait and final commit time. This distinguishes expensive output handling from slow provider progress and database saturation.

    Pilot pass. Stall output storage and kill a worker after a file write but before result commit. Keep success hidden until publication, recover the original handle, and expose one result manifest. Verify that a temporary file without committed metadata is eventually cleaned up. Inspect artifact preparation

    SSE reconnect and replay

    Observed. The provider worker owns upstream execution and appends encrypted chunks with an ordinal. An API reader reauthorizes each read and streams committed chunks to the client. Losing that reader leaves the worker running.

    Caller action. Follow the request’s Location for lifecycle status. To recover retained text, send the same streaming request and idempotency key. Replay starts at the beginning, so replace the partial transcript with the replay. After expiry or removal, report content unavailable and retain the same request for status and usage.

    Pilot pass. Disconnect mid-stream, reconnect with the original key, and confirm the same request and one upstream invocation. Check that the rebuilt transcript matches the completed text. Inspect the SSE reader

    Webhook delivery recovery

    Observed. Eligible terminal events are committed with stable delivery IDs. Retries and redrive preserve webhook-id and the payload. Delivery and inference have independent states.

    Receiver and operator action. Verify the signed raw body and timestamp. Use webhook-id as a unique key and commit it with the receiver’s side effect before returning 2xx. Check the scoped request status for the inference outcome. For delivery, inspect pending/dead counts and oldest age in Queue backlog, then open the project’s delivery attempts. Fix the destination and redrive an eligible dead delivery with an active subscription.

    Pilot pass. Commit the receiver’s side effect and drop its response. Confirm that retry and redrive carry the same ID, the side effect happens once, and inference stays succeeded. Inspect webhook delivery · Queue backlog
